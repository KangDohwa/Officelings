# Reproducible offscreen measurements

Build the product in Release before measuring, then stop other builds/tests/performance processes. The harness references copied, unchanged App/Core assemblies through the existing `Vibedotcom.Tests` friend assembly. It does not build product sources. Each output directory must be new; existing results are retained.

```powershell
$perfAppBin = "$PWD/src/Vibedotcom.App/bin/Release/net10.0-windows"
$perfBefore = "$PWD/tools/perf/results/my-before"
powershell -NoProfile -ExecutionPolicy Bypass -File tools/perf/benchmark.ps1 -Mode All -AppBin $perfAppBin -Output $perfBefore
# Build and Run can be coordinated separately:
powershell -NoProfile -ExecutionPolicy Bypass -File tools/perf/benchmark.ps1 -Mode Build -AppBin $perfAppBin -Output "$PWD/tools/perf/results/my-after"
powershell -NoProfile -ExecutionPolicy Bypass -File tools/perf/benchmark.ps1 -Mode Run -Output "$PWD/tools/perf/results/my-after"
$py = 'C:/Users/myori/.codex/skills/sprite-gen/.venv/Scripts/python.exe'
& $py -B tools/perf/summarize.py $perfBefore --output "$perfBefore/summary.json"
& $py -B tools/perf/summarize.py tools/perf/results/my-after --output tools/perf/results/my-after/summary.json --baseline "$perfBefore/summary.json"
& $py -B tools/perf/compare-pixels.py "$perfBefore/pixels" tools/perf/results/my-after/pixels --output tools/perf/results/my-after/pixel-comparison.json
# Detailed diagnostics from actual decoded PNGs, including changed-pixel count/bounds/channel delta:
& tools/perf/results/my-after/harness/bin/Vibedotcom.Tests.exe pixel-diff tools/perf/results/my-after/pixel-diff "$perfBefore/pixels" tools/perf/results/my-after/pixels
```

The default settled workload is 0 agents and 12 working agents, normal/topmost/transparent, in three fresh sequential processes per condition. Working agents settle for 120 logical seconds before live warmup. Live windows are 720x480 at (-30000,-30000), 1x, nonactivating, absent from the taskbar; QA suppresses save/tray/hover and uses an explicitly isolated tracker home. Polling is disabled so it cannot replace fixed agents. No foreground/input/minimization/desktop-hosting operation is performed. Native topmost, transparency and no-activate style checks are recorded. The empty live office includes the built-in three-frame 3 FPS TV; it is not a static-empty deadline test.

The default suite also runs three `Activities` repeats in each mode with 12 native idle agents after 90 logical seconds of leisure/wandering, and three normal-mode `Polling` repeats with zero agents and actual product polling against a newly created empty home. External activities report moving animation ticks and maximum moving characters; CPU remains mixed activity, with no moving-only CPU claim. Internal historical samples separately record moving poses at interval endpoints. Polling records actual tracker last-poll timestamps at the bounds, not an invented poll count. Use `-ActivityModes normal` for shorter activity coverage. `-Suite` can select only required phases; `-Resume` keeps completed repeats and writes new directories for interrupted repeats.

The current live suites use `collect-external.ps1`. Target windows have two finite measurement callbacks, after 10 seconds of warmup and approximately 15 seconds of measurement. One-second process CPU/memory/thread queries execute in the separate PowerShell collector. The target records native process/UI CPU, allocation, app timer and damage deltas at the bounds. Aggregate CPU uses those full target bounds; periodic median/p95/max exclude partial edge intervals. No observer estimate is subtracted. Allocation/counter rates derive from totals, not fabricated per-second samples. UI thread identity is known; other CPU includes all non-UI threads and cannot be labeled exclusively WPF render. `cpuOneCorePercent = 100 * cpuSeconds / wallSeconds`; `cpuMachinePercent = cpuOneCorePercent / logicalProcessors`. One core continuously busy is 100%. A zero one-second median can reflect Windows CPU accounting granularity; retain aggregate averages. `appScheduledWakeups` counts callbacks on product DispatcherTimer fields, not OS/ETW wakeups. Unsupported counters are null. Offscreen results do not establish visible compositor performance.

`-Suite Observer` runs three blank-window controls with the original internal counter/memory sampler and no product animation or timers. Internal `live ... [threads]` optionally captures thread CPU/descriptions. Sampler callbacks report wall time, UI CPU, current-thread allocation and separate counter/memory/thread query times; observer cost is measured, not assumed small. Historical internal live results include this observer cost and remain separate from external measurements. Earlier `animationWakeups` counts only the animation timer; QA-disabled hover contributes no callbacks. Maintenance method counters can increment within animation callbacks. Build checks DLL SHA-256; runtime.json records actual loaded SHA-256/MVID.

`Startup` uses three fresh harness processes, invokes the product's `LoadOfficeAsync` and constructs its normal OfficeWindow with explicit isolated storage. It records decoded sheet counts after loading, construction and first ContentRendered, plus loader/constructor/first-render timings and process-start-to-first-render time. It never explicitly calls DecodeSheets. This is an owned offscreen first-render measurement through the actual loading strategy; visible foreground launch latency and a 1.5-second visible-startup target remain unverified.

`phases` warms up 20 calls (3 for RenderBitmap) then measures 500 Core.Update, AssignWorkplaces, RefreshFurniture and View.Update calls, 100 direct OnRender calls, and 8 complete RenderBitmap calls for each count. Stopwatch and `GC.GetAllocatedBytesForCurrentThread` bracket each call; fixture setup, result serialization and sample arrays are excluded. Reflection calls include their overhead; the ToString reflection control is reported, not subtracted. Whole Core.Update includes its subphases. View.Update uses a fixed settled snapshot; OnRender records into a DrawingContext without rasterization. RenderBitmap includes layout/dispatcher processing, OnRender, hidden HWND lifecycle and bitmap rasterization. Those render numbers cannot be subtracted to estimate an isolated overhead, and retained rendering can move work between Update/OnRender.

`counts` discards 40 updates then executes exactly 240 updates at 125 ms logical intervals using one persistent hidden presentation source, with no forced invalidation or bitmap capture. The 0-agent `static-empty` fixture has no furniture, overflow seats or generated desks. The 12-agent fixture uses the normal office. It reports Core and View+dispatcher thread allocations separately, whole-process allocation, scene/dynamic/room draw counts and logical redraw area. Product `RedrawPixelArea` sums changed drawable bounds in viewport pixels; it is not an OS/compositor counter and overlaps can be counted more than once. For older full-scene assemblies without it, full OnRender count times the measured viewport area is explicitly labeled as the baseline estimate. Static root draw counts remain separate.

For a changing-frame allocation diagnostic, run `<Harness> changing-tv <NEW_OUTPUT>`. It preserves the default animated furniture, discards 30 logical frames and measures 300 frames near 3 Hz, for 0 and 12 settled working agents. Core.Update, View.Update and dispatcher draining have separate stopwatch/thread-allocation brackets. It then measures one whole-office FurnitureDepth pass per sample through reflection, plus a separate control with the same reused argument array and boxed double return. Counts and invocation overhead stay explicit; this supplemental diagnostic is not the fixed-snapshot phase measurement or a live CPU result.

The summary retains each repeat's median/p95/max and reports the minimum of exactly three medians. With `--baseline`, it gates comparable allocations, fixed update counts, scene/room draws, live wakeups and logical area, with a default 10% tolerance; CPU and elapsed timings do not gate. Rendering allocations are compared as View+dispatcher combined work, because moving draw work from OnRender into retained Update changes the phase boundary. Missing conditions/repeats fail the comparison. Each raw sample stays available. The nine demo pixel fixtures use seed 42, epoch `2026-10-04T00:00:00Z`, 100 ms steps from -18 s, captures at 0/12/36 s and 1/2/3x, and exact Pbgra32 SHA-256 comparison.

To pause a running benchmark between processes, create `<Output>/pause.request`; remove that owned marker after the other build/test finishes. This does not interrupt a measured interval. `soak.ps1` uses the same sequential three-repeat collector; `analyze.ps1` only reads the historical CSV format and writes a new summary, while `summarize.py` reads the current harness JSON. `tracker/tracker.ps1 -Mode Build -CoreDll <Release Core DLL>` requires an explicit assembly; its separate fixture run remains a synthetic JSONL workload and reports both CPU percentages.
